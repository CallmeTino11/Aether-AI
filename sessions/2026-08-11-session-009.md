## Objective

Close the three gaps between a working codebase and something a real customer could use: real authentication, real notification delivery, and a scheduler to run the worker.

## Work Completed

### Authentication — using a library, deliberately

`resolveUser` was an injected port with a test fixture behind it. It now verifies real Supabase tokens.

I used `jose` rather than hand-rolling this, and the reasoning is worth recording because writing it by hand looks easy. JWT verification is base64 decoding plus a signature check — which is exactly why hand-rolled versions keep failing the same four ways: `alg: none` accepted as valid, algorithm confusion, unchecked expiry, and non-constant-time comparison. These are solved problems and reimplementing them invents risk for nothing (DEC-0019).

The part that still needed care is **algorithm pinning**. Without it, a token can declare `alg: HS256` against a project configured for asymmetric keys, and the RS256 *public* key gets used as the HMAC secret — public material becomes a signing key and anyone can mint a token for any user. There is a test that runs this attack against a live JWKS endpoint and asserts it fails.

**A real bug this caught:** expiry detection matched on the error *message*. jose's message for an expired token is `"exp" claim timestamp check failed` — it contains no form of the word "expired", so my check never matched. Every expired session would have been reported as `invalid_token`, sending users to a login screen instead of a silent token refresh. Fixed by matching the structured error code, which is more robust than string-sniffing regardless.

### Delivery — a real provider, and permanence

Added a Resend adapter (plain HTTP, no SDK, ~60 lines). Provider choice stays a business decision; swapping to SES or Postmark is another class against the same port.

One behaviour worth noting: the sender distinguishes **permanent** failures (4xx — a rejected address will fail identically forever) from **retryable** ones (5xx, 429, network). The worker now abandons permanent failures on the first attempt rather than burning all six, which surfaces a bad address to the business in seconds instead of half an hour.

### Scheduling — a public endpoint that drains a queue

Serverless schedulers invoke work over HTTP, so the "scheduler" is a URL, and that URL is reachable by anyone. Unauthenticated, a stranger could drain the notification queue and trigger provider calls at will. It requires a shared secret compared in constant time, and refuses to be constructed with a secret under 16 characters — a cron endpoint silently running unauthenticated is worse than one that fails loudly, because nothing about its behaviour would look wrong (DEC-0021).

Housekeeping failures are logged rather than failing the run: delivery is the job, cleaning old rate-limit rows is not worth failing an invocation that delivered successfully.

### Composition root and fail-fast config

`src/app.ts` is now the only file reading environment variables. Configuration is validated eagerly, and production additionally requires an email provider and a non-empty widget origin allowlist (DEC-0020). Each of those would otherwise produce a deployment that looks healthy and fails in front of a customer: alerts queuing forever while the dashboard says "pending", or a widget that silently never loads on the customer's site. The AI model has no default, because a fallback would mean cost and answer quality chosen by omission.
