### The Next.js site is a separate app, not folded into the core deployment

`web/` has its own `package.json`, deployed as its **own Vercel project**, rather than merging into the existing `api/`+`public/` Vercel project. The core app (widget, dashboard, cron, now leads) is tested and already deploy-ready (DEC-0024); bolting a Next.js build onto the same project risked its `outputDirectory: "public"` static-plus-serverless-functions setup for no real benefit. The marketing site calls the core API's public endpoints over plain cross-origin `fetch`, the same contract `public/widget.js` already uses.

Both pages (`web/app/page.tsx`, `web/app/pricing/page.tsx`) reproduce the approved mockups' structure, tokens, and copy as real React components — verified by screenshot against a running `next dev`, not just "it typechecks."

### The live demo tells the truth about what's real

Only the Receptionist is a built product. The "try before you hire" role picker's Receptionist card is backed by a real conversation (session-token auth, DEC-0012) against a seeded demo tenant when `NEXT_PUBLIC_AETHER_API_BASE` and `NEXT_PUBLIC_DEMO_RECEPTIONIST_EMPLOYEE_ID` are both set; Support and Sales Rep stay the mockup's scripted, labeled preview, because those roles don't exist yet. Without both env vars, Receptionist falls back to the same scripted preview rather than claiming to be live — DEC-0017 (don't claim an action, or a capability, the system doesn't have) applies just as much to marketing copy as to a widget's "team notified" message.

### Lead capture reused the existing outbox rather than inventing a second one

A prospect asking about Aether AI through the pricing page's CTAs isn't a tenant's own customer — the existing `leads` table (migration 0001) is RLS-scoped to a real business, and a prospect has no business yet. Built `signup_leads` instead (migration 0006), RLS-enabled with zero policies (service-role only, same pattern as the anonymous widget path), and widened `notification_outbox.kind` to accept `'lead'`. A single seeded "house" business row anchors these alerts so the tested outbox/worker/backoff machinery (DEC-0015, DEC-0016) delivers them unchanged, rather than a second delivery pipeline being built from scratch.

### A real bug surfaced by adding the second kind

`PgNotificationOutboxRepository.claimDue` hardcoded `kind: "escalation"` on every claimed row. Harmless while escalation was the only kind that existed; it would have silently mislabeled every lead notification as an escalation once this shipped. Fixed to read the row's actual `kind`, and added an integration test (`notifications.integration.test.ts`) asserting a claimed lead entry reports `kind: "lead"` — this is the regression test for exactly that bug, gated the same way as the rest of the suite (skips locally without `DATABASE_URL`, hard-fails in CI per DEC-0011).
