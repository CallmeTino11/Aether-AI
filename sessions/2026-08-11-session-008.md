## Objective

Make the product self-serve: an owner should hire an employee, teach it, choose who gets alerted, and review what it couldn't answer — without anyone inserting rows by hand.

## Work Completed

### The dashboard is the first place RLS actually matters

Every surface so far ran as the service role with RLS bypassed and the application as the sole boundary. The dashboard is the opposite: a real user is logged in, so Postgres can enforce tenancy directly. That is stronger — but only if the user's identity is set correctly on every statement, and two Postgres behaviours make the obvious approach unsafe. I tested both before designing around them:

**1. Session-level `set_config(..., false)` persists after commit.** I set an identity, committed, then ran a fresh statement on the same connection: it still returned the old subject. With connection pooling that is one user reading another user's business, while every RLS policy remains present and correct. No policy review would catch it.

**2. Transaction-local `set_config(..., true)` reverts to the *session* value, not to null.** So "clearing" identity restores a stale one rather than none.

There is a third trap that needs no experiment: **Postgres exempts table owners from RLS.** Running dashboard queries as the owner would leave every policy in place, every policy test passing in isolation, and every policy bypassed in production.

The executor therefore never touches session-level configuration, runs every statement inside a transaction with transaction-local identity, and assumes a non-owner role (`app_user`, migration 0004). Outside a transaction there is no identity at all, so RLS denies everything — failing closed (DEC-0018).

`DashboardService` deliberately contains **no** `business_id = ?` filters. Adding them would imply the database is not already enforcing tenancy, and would hide a broken policy behind an application check that happened to compensate.

### Test isolation bug caught by the repeat-run guard

The suite failed on run one and passed on run two — the inverse of session 006's symptom, and only visible because DEC-0014 added the second run.

Cause: `node --test` parallelises test *files*; these files share one database; and the notification worker claims from a **global** queue by design. So a worker test can claim outbox rows another file just created. I confirmed the mechanism by seeding stray pending rows for an unrelated business and watching the worker lease them.

Fixed by running integration files serially. That is the honest fix: they share a database, so pretending they are independent was the error.

### Built

- Roster, knowledge, recipients, escalation review, and knowledge-gap grouping (repeated unanswered questions, so escalations become a to-do list rather than a pile)
- Dashboard API with identity from a verified token only
- `public/dashboard.html` — designed as a staff roster and handover notes rather than a SaaS console, matching the product's premise that hiring should not feel like configuring software. The escalation note sets the customer's actual question large, because that sentence is the only thing an owner needs to read. Each note states plainly whether anyone was really alerted (DEC-0017).
