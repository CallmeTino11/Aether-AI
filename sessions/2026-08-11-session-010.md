## Work Completed

### SMS — implemented rather than removed

The dashboard offered SMS recipients while no sender existed, so every such alert failed permanently. Two options: remove the option or implement it. Implementing it is worth more — SMS is the channel a small business owner actually notices.

The interesting part is not the API call but the **cost model**. SMS bills per 160-character segment, so mailing a full escalation body would cost several messages per alert and arrive as a wall of text on a phone. Alerts now render a separate short body budgeted to one segment, with the conversation link given its budget first (it is the actionable part) and the customer's question filling what remains, truncated at a word boundary. Full detail stays in the email and dashboard — nothing lost, only relocated (DEC-0022).

**Bug found:** the adapter classified failures by Twilio's error code *whenever one was present*, ignoring HTTP status entirely. An unrecognised code on a 400 was therefore treated as retryable and would burn all six attempts re-sending a request the provider had already rejected. A test asserting the status fallback caught it. Both signals are now used: a known-permanent code, or any non-429 4xx.

`DeliveryError` also moved out of the Resend adapter into the application layer — both senders raise it and the worker interprets it, so leaving it in one provider's file would have made the other import a peer it has nothing to do with.

### Proving the provider abstraction

Provider-agnosticism has been claimed since session 002, but with one implementation it was an assertion. An abstraction with a single implementation is a guess about what varies.

Added an OpenAI adapter and a suite that runs the **same `ReceptionistEngine`** against both vendors. Differences the adapters absorb, none of which reach business logic:

| | Anthropic | OpenAI |
|---|---|---|
| System prompt | top-level `system` field | first message in the array |
| Token counts | `input_tokens` / `output_tokens` | `prompt_tokens` / `completion_tokens` |
| Response body | content-block array | `choices[0].message.content` |
| `temperature` | accepted | rejected outright by reasoning models |

The most valuable assertion is that the **grounding safety rule holds identically on both**: with no matching knowledge, neither provider is called at all. A safety property that depended on which vendor was configured would not be a safety property (DEC-0023).

### Deployment surface

Three thin serverless entry points wrapping the composition root, plus routing, cron schedule and caching in `vercel.json`. The handlers were already written against web-standard `Request`/`Response`, so these are genuinely thin and the platform stays replaceable. The app is built lazily on first request rather than at module load, so a configuration error surfaces with a useful message instead of an opaque platform crash (DEC-0024).

**Also fixed:** the production build was shipping test files. Now excluded via `tsconfig.build.json`.

`docs/Deployment.md` documents the full path from repository to running service, including the two CORS rules that look contradictory but are not: `widget.js` is public static JavaScript any customer site must load, while the API is credentialed and keeps a strict allowlist.
