## Work Completed

### The security problem the roadmap didn't mention

The widget is an **unauthenticated write path**. An anonymous visitor creates and continues a conversation with no Supabase session, so it must run under the service role with RLS bypassed — which means RLS (DEC-0007) protects nothing on this path and the application becomes the only authorization boundary. Two holes had to be closed before an endpoint could exist:

**1. Conversation hijacking (DEC-0012).** A conversation id alone is not a credential. UUIDv4s are unguessable, but they are not secrets: they appear in logs, referrer headers, and support tickets. Anyone holding one could post into a stranger's conversation and read the replies. Conversations created anonymously now carry a separate 256-bit session token, stored only as a SHA-256 hash — the plaintext is returned once and never persisted, so a database dump yields no live credentials.

**2. Unbounded cost (DEC-0013).** Every turn is a paid provider call. An unlimited anonymous endpoint is an unbounded bill on a customer's account. Fixed-window limits now apply per conversation (20/min) and per business (300/min) — both scopes are needed, since per-conversation limits don't stop a script opening many conversations. Ordering is deliberate: **authorize first** so an attacker can't burn a victim's quota, **limit before the provider call** so a rejected turn costs nothing.

Counting is an atomic SQL function, not read-modify-write. Verified with 20 parallel database connections (exactly 20) and 25 concurrent application calls (exactly 25); a read-modify-write would have lost updates and admitted extra paid turns.

### Built

- Migration 0002: token hashes, `last_activity_at`, atomic counters
- Session token module: CSPRNG generation, SHA-256 storage, timing-safe comparison
- Widget service: the transport-agnostic security boundary
- HTTP handler on web-standard `Request`/`Response` — runs in Next.js, Vercel edge, or plain Node with no adapter, so DEC-0005's framework choice stays a deployment detail
- `public/widget.js`: dependency-free, Shadow DOM isolated, keyboard accessible, `aria-live` for screen readers. **All text via `textContent`, never `innerHTML`** — model output reading business-supplied knowledge is untrusted input for rendering, and having an escalation path is no excuse for an XSS hole.

### The bug worth recording (DEC-0014)

The suite passed 20/20, then failed when run again. The rate-limit tests inject a **fixed clock** so window boundaries are deterministic — which also means the same `(scope, key, window)` counter row is reused every run. Cleanup deleted only `widget-test%` keys and missed the business-scope keys (UUIDs), so leftover counters from the first run made the business-limit test trip on its **first** message instead of its third.

The first green run was luck, not evidence. Fixed the cleanup, then verified three consecutive full runs at 29/29, and CI now runs the suite twice so this cannot silently return.

This is the third false-confidence defect in this codebase, after the subshell exit-code bug (DEC-0008) and silent integration skips (DEC-0011). Same shape every time: something reported success without having verified anything.

### Verified

29 integration tests, three consecutive runs. 12 widget-security tests attempt the actual attacks; 9 HTTP tests drive a real server with real `fetch`.

## Risks
- **The escalation promise is unfulfilled.** The widget tells customers a team member was notified. Until notifications exist, that message overstates reality — worth fixing before any real customer sees it.
- Widget CORS is an explicit allowlist, which is correct but means onboarding a customer requires adding their domain. That belongs in the dashboard.
- `MAX_MESSAGE_LENGTH` (2000) is enforced server-side and mirrored in the widget's `maxLength`; the two constants could drift.
