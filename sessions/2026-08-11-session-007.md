# Session

**Date:** 2026-08-11
**Participants:** Founder (delegated authority, DEC-0003), Claude

## Objective

Close the broken promise recorded in session 006: the widget told customers "a team member has been notified" while nothing in the system notified anyone.

## Work Completed

### Why an outbox and not an email call

The naive fix — call an email API when a turn escalates — fails three ways: third-party latency lands in the customer's response path, the alert vanishes if the provider is down, and a crash between "mark escalated" and "send alert" loses it with no trace.

So the alert is written to `notification_outbox` **in the same transaction as the escalation**, and a worker delivers it with backoff (DEC-0015). Either both writes land or neither does. The outbox row is a *parameter to `appendTurn`*, not a separate call afterwards — atomicity that a caller can forget is not a guarantee.

### The bug worth the session

The claim function used `for update skip locked`, which is the textbook answer for multi-worker queues. I tested it with six concurrent workers against 30 due rows before building on it:

**50 claims across 30 unique ids — 20 rows claimed more than once.**

`SKIP LOCKED` protects *concurrent* transactions. Once the claiming transaction commits, the row is still `pending` and still due, so the next worker takes it again. In production that is duplicate escalation emails to a customer's team.

Fixed by also **leasing** the row on claim: `next_attempt_at` moves forward, making it invisible until the lease expires (DEC-0016). Retested: 30 claims, 30 unique, zero duplicates. The lease also gives crash recovery for free — a worker that dies mid-delivery releases its rows automatically.

A second defect surfaced during the fix: adding the lease as a *defaulted* argument made `create or replace` produce a second overload instead of replacing the old function, so every call failed with "function is not unique". The argument is now required.

**Regression guard:** I restored the buggy function and confirmed the new test fails against it (reproducing 50 claims / 30 unique) before restoring the fix. A test that has never been observed to fail proves nothing.

### The honesty fix

`teamNotified` now flows from the persistence layer to the widget. The widget says "a team member has been notified" only when an alert was genuinely queued; otherwise it says it has flagged the conversation. The development console sender throws on `NODE_ENV=production`, because a sender that silently succeeds would mark alerts delivered that no human ever saw (DEC-0017).

A false reassurance is worse than an honest limitation: the customer stops chasing, the business never learns, and it surfaces as lost trust rather than as a bug.

- `MAX_MESSAGE_LENGTH` is still duplicated between server and widget and could drift.
